# Contributing

## The one rule that overrides everything else

**Never commit anything derived from a retail cartridge image.**

Not the ROM, not an extracted `arm9.bin`, not a generated `.s`, not a decoded
texture, not a sound bank, not a "harmless" hex snippet pasted into a comment,
not a checksum-of-the-ROM-plus-the-ROM-itself in a fixture. `.gitignore` covers
the directories these belong in and `RepoHygieneTest` fails the build if one
slips through, but neither is a substitute for paying attention.

If you are unsure whether something is derived from the ROM: it is. Leave it out
and describe it in prose instead.

The single exception is `tests/data/testrom.nds`, generated by
`tests/make_test_rom.py` from code written for this repository. It is not a dump
of anything. Even so, it is regenerated on demand rather than committed.

## Getting started

```sh
git clone <this repository>
cd Rush-Decomp
make setup
```

`make setup` verifies the toolchain end to end against the synthetic image
without you needing a ROM at all. Do this before touching anything, so that you
know whether a later failure is yours or pre-existing.

Then put your own dump at `baserom/sonic_rush.nds` (see `docs/ROM_SETUP.md`) and
run `make report` to confirm which revision you have.

## What needs doing

Ordered roughly by how useful each is per hour of effort:

1. **Name things.** The disassembly is full of `func_02001A80`. Finding out what
   a function is called — from string references, from Nitro SDK conventions,
   from behaviour in an emulator — is the highest-value contribution there is,
   and it needs no toolchain at all.
2. **Resolve indirect branches.** `asm/<name>.json` lists every `bx rN` /
   `blx rN` as an unresolved tail. Each is a jump table or a function pointer
   waiting to be identified. Work through them and record what you find.
3. **Map the file system.** `make dumpfs` gives you every asset with its path.
   Identifying which format is which (and there will be formats nobody has
   documented) unblocks a lot of later work.
4. **Convert a function to C.** Pick a small leaf function with no indirect
   calls, write it in `src/`, and annotate it. See below.
5. **Improve the toolchain.** Every Capstone/Keystone spelling disagreement you
   hit is a one-line fix in `assembler.normalise()` that saves the next person
   an hour.

## Converting a function

Create a file under `src/`, mirroring the component it came from:

```
src/arm9/game/player.c
src/arm7/sound/driver.c
src/arm9_overlay_012/zone/boss.c
```

Annotate every function you reproduce. The annotation is how progress is
counted, and how the byte total is checked against the disassembly:

```c
/*
 * @rush_match arm9 0x1c4 func_02001A80
 */
void Player_Update(Player *player)
{
    /* ... */
}
```

The format is `@rush_match <image> <byte-count> <original-symbol>`, where the
byte count is what the disassembly says that function occupies. `sr progress`
verifies it: an annotation naming a symbol that does not exist, or a byte count
that disagrees with the disassembly, is reported as a problem rather than
counted silently. That is the point — the progress number has to mean something.

Delete the function from `asm/<image>.s` once your C replaces it, so the two
cannot drift.

## Style

- Python: 4 spaces, type hints on public functions, `from __future__ import
  annotations`. Run `make lint`.
- Docstrings explain *why*, not *what*. A comment that restates the code is
  noise; a comment explaining that `0x30` is not a valid LZ77 marker and that
  this is deliberate is worth its weight.
- C under `src/`: match the original's structure, not modern taste. If the
  binary shows a function taking a struct by value in a way you find
  distasteful, reproduce it faithfully and add a comment saying so.
- Commit messages: imperative mood, first line under 72 characters, body
  explaining the reasoning. "Fix ARM7 compression detection" plus three
  sentences about why byte-sniffing is unsafe beats a one-liner.

## Heuristics are allowed. Silent ones are not.

Recovering code structure from a symbol-less binary is guesswork by nature. What
is not acceptable is guesswork that cannot be diagnosed. Every heuristic in
`disasm.py` is documented at the top of the module with the failure mode it
prevents, and every one records what it decided in the JSON sidecar.

If you add a heuristic, document:

- what it assumes,
- what breaks when the assumption is wrong,
- how someone would tell that it had broken.

## Pull requests

- Run `make check` before pushing. CI runs the same thing and will fail on the
  same grounds, so there is no advantage in skipping it.
- Keep ROM-derived output out of the diff. If `git status` shows files under
  `data/`, `asm/`, `fsdump/`, `build/` or `baserom/` as untracked, that is
  correct and expected — leave them untracked.
- A PR that improves a heuristic should include the test that pins the new
  behaviour, ideally added to `tests/make_test_rom.py` so the synthetic image
  exercises it too.

## Legal

This project exists to study and understand a commercial game, in the tradition
of other decompilation and preservation efforts. It distributes no ROM, no
extracted asset, and no copyrighted code. What it distributes is original
tooling and documentation, plus whatever reconstruction contributors write
themselves.

You are responsible for how you use it. Dump your own cartridge, keep the output
on your own machine, and do not upload what `.gitignore` excludes.
